## 單槽測試當時的方向

本節保留單槽測試背景；目前整合版需求以 [設計定案](DESIGN.md) 為準，已改為六槽及合計適應性決定速度。

- 一隻具發電適應性的帕魯占用一台機器；封裝期間不可同時作其他用途，取回的是同一隻帕魯。
- 使用者接受觀賞籠容器不占基地工作名額，成本為占用該帕魯個體。現有截图的基地人數維持 38/50，尚非所有移入來源或多人模式的計數驗證。
- 完成整合後，只有發電適應性決定兌換速度，10 級最快；實際時間尚未定案。
- 晶石維持 1:1。此次不增加派工、SAN、飢餓或工作速度計算。

## 這個原型實際做了什麼

新增 `PAE_ContainmentProbe`，顯示名稱為 **Awakening Crystal Core（封裝測試）**。科技第 1 級、0 點、木材 1 個僅供測試。外觀為平台與四根立柱，並非正式罐體。

採原生 `PalMapObjectDisplayCharacterModel` 與角色容器，`SlotNum=1`、`RecoverAmountBySec=0`。存入、取回、保存及拆除交給此原生模型。Lua 沒有複製帕魯、清空來源槽、寫入存檔或改 SAN；但原生角色在新建築中的實際狀態仍需實测，不能由「沒有自行扣 SAN」推定狀態一定不變。

既有兌換機的配方、工作參數及介面不變。此版新增篩選只作用於 `PAE_ContainmentProbe` 的原生觀看籠介面，檢查 `GetWorkSuitabilityRankWithCharacterRank(GenerateElectricity)`。不合資格時保留來源帕魯，抑制當次移入呼叫。這不是多人伺服器完整權限限制；拖曳或其他移入入口是否繞過篩選仍待實测。

開啟介面及容器內容變化時，以 `[AwakeningCrystalCore]` 記錄機器 ID、容器 ID、格數、帕魯個體 ID、發電適應性、SAN 與 `HungerParameterRate()` 回傳值，供同一隻帕魯的前後核對。該函式回傳值不作為目前飽食度比例的證據，實際飽食度仍以介面數值核對。無持續掃描或自動狀態修正。

## 為何先分開測試

目前 SDK 與實際原生函式顯示，古代文明配種器的親代使用基地派工／隱藏工作模型；現有兌換模型則沒有暴露新增角色容器的註冊入口。觀看籠的原生角色容器是目前可直接驗證的保管路徑。

單槽保管成功後，才決定與既有兌換模型的結合方式；不把獨立測試台宣稱為完整封裝兌換機。

## 遊戲測試順序

1. 測試世界建造並開啟測試台，確認只有一槽。先驗證空台載入，再投入帕魯。
2. 用可供測試的發電帕魯存入，確認來源不再保有該個體；核對介面適應性，並確認無法同时加入隊伍或派至其他工作。
3. 從原生介面取回，核對同一個體、等級與技能。尚未通過這一步前不使用重要帕魯。
4. 再次存入，正常退出並重開，確認容器占用和個體 ID 保留，再取回。
5. 比較封裝前後 SAN／飢餓是否有意外變化，測試無發電適應性帕魯的其他移入入口。
6. 前述通過後，再在測試世界驗證有內容時拆除的原生處理，以及兩台測試台互相隔離。

所有保管案例通過後才連接兌換，驗證空槽停止、取回停止、不同適應性速度，以及原有指定數量完成後停止。多人模式另行驗證。
